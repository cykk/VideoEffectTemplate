# 前端浏览器基址配置约定

## 目的

统一约定前端在浏览器环境下访问不同后端能力时，应使用哪个基址，避免后续因为“全部同源”或“全部直连 API”的误改导致登录、SSE 或业务接口异常。

当前项目采用以下正式方案：

- 业务 API 同源
- SSE 同源
- Auth 直连 API

---

## 配置项说明

### 1. `NEXT_PUBLIC_BROWSER_API_BASE_URL`

用途：

- 浏览器端普通业务 API 请求基址
- 例如图片处理状态查询、下载链接、用户积分、反馈提交等常规接口

约定：

- 应配置为 Web 同源地址

推荐值：

- 生产：`https://watermarkremover.tech`
- 本地开发：`https://web-dev.watermarkremover.tech`

原因：

- 浏览器侧接口体验更统一
- 降低 CORS 心智负担
- 由 `apps/web` 的 `/api/*` 代理统一转发到真实 API 服务

---

### 2. `NEXT_PUBLIC_BROWSER_SSE_BASE_URL`

用途：

- 浏览器端 SSE 事件流连接基址
- 例如用户任务状态流、处理进度推送等

约定：

- 应配置为 Web 同源地址

推荐值：

- 生产：`https://watermarkremover.tech`
- 本地开发：`https://web-dev.watermarkremover.tech`

原因：

- SSE 长连接走同源更稳定
- 减少跨域连接、凭证携带和调试复杂度
- 与普通业务接口保持一致，便于前端统一处理

---

### 3. `NEXT_PUBLIC_BROWSER_AUTH_BASE_URL`

用途：

- 浏览器端认证相关请求基址
- 包括 Better Auth、OAuth 启动、session 获取、登录/登出等

约定：

- 应配置为 API/Auth 直连地址

推荐值：

- 生产：`https://api.watermarkremover.tech`
- 本地开发：`https://api-dev.watermarkremover.tech`

原因：

- OAuth、302 跳转、callback、`Set-Cookie`、session 建立对中间代理层更敏感
- Auth 直连 API 能减少一层转发，提升登录链路稳定性
- 当前项目的 Google 登录问题已通过该方案验证解决

---

## 当前推荐组合

### 生产环境

```env
NEXT_PUBLIC_BROWSER_API_BASE_URL=https://watermarkremover.tech
NEXT_PUBLIC_BROWSER_AUTH_BASE_URL=https://api.watermarkremover.tech
NEXT_PUBLIC_BROWSER_SSE_BASE_URL=https://watermarkremover.tech
```

### 本地开发环境

```env
NEXT_PUBLIC_BROWSER_API_BASE_URL=https://web-dev.watermarkremover.tech
NEXT_PUBLIC_BROWSER_AUTH_BASE_URL=https://api-dev.watermarkremover.tech
NEXT_PUBLIC_BROWSER_SSE_BASE_URL=https://web-dev.watermarkremover.tech
```

---

## 不要误改的原则

### 不要把 Auth 改成 Web 同源

不建议把：

- `NEXT_PUBLIC_BROWSER_AUTH_BASE_URL`

改成：

- `https://watermarkremover.tech`
- 或 `https://web-dev.watermarkremover.tech`

原因：

- OAuth 和 session 链路会重新穿过 web 代理层
- 会增加重定向、Cookie、callback 排障复杂度
- 当前项目已经验证过：Auth 直连 API 更稳定

### 不要把 SSE 改成直连 API，除非有明确重构需求

原因：

- SSE 跨域连接复杂度更高
- 同源更符合当前项目的前端连接模型

---

## 配套关系

本约定依赖以下部署事实：

- Web 站点与 API/Auth 服务为双域部署
- Web 侧存在 `/api/*` 代理转发能力
- Auth Cookie 使用顶级域共享

相关配置通常包括：

- `NEXT_PUBLIC_WEB_URL`
- `NEXT_PUBLIC_APP_URL`
- `BETTER_AUTH_URL`
- `BETTER_AUTH_TRUSTED_ORIGINS`
- `AUTH_COOKIE_DOMAIN`
- `API_UPSTREAM_URL`

---

## 适用结论

在当前项目架构下，推荐长期保持：

- 业务 API 同源
- SSE 同源
- Auth 直连 API

除非未来发生以下重构，否则不建议调整：

- Web 与 API 完全单域合并
- 取消独立 Auth/API 域
- 整体实时通信方案改造

# 前后端边界开发约束

## 1. 目标

当前仓库已经重构为：

- `apps/web`：前端站点
- `apps/api`：后端服务
- `packages/shared`：共享类型、配置、i18n、通用库

本约束用于保证：

- `Vercel 前端 + Fly.io 后端` 的职责边界长期稳定
- 不把认证、数据库、支付、任务处理重新写回前端页面层
- 当前仓库可以持续作为后续新产品的启动模板

## 2. 核心原则

- 前端负责页面、交互、展示和轻量 SSR
- 后端负责认证、数据库、支付、订阅、积分、上传、Webhook、SSE 与任务处理
- 公共类型、常量、i18n、基础工具与共享服务封装放在 `packages/shared`

## 3. `apps/web` 可以做什么

- 页面、布局、营销页、用户界面
- 通过共享的 `backend-fetch` / `apiFetch` 调用 `apps/api`
- 处理 SEO、静态内容、字典与路由层逻辑
- 做轻量的页面协调、跳转与降级展示
- 渲染后台页面，但后台数据必须通过后端 API 获取
- 后台页面优先采用浏览器直连 `apps/api` 的客户端模式
- RootLayout 保持服务端壳，用户态 Header / Footer 数据统一由客户端 `AppShell` 拉取

## 4. `apps/web` 不应做什么

- 不应在页面层直接承接核心写操作
- 不应在普通业务页面中直接处理支付、积分扣减、任务状态写入
- 不应把上传、Webhook、视频处理等核心后端能力放回 `web`
- 不应在后台页面中直接查询数据库、Redis 或系统状态

说明：

- 当前后台页面的数据读取已经统一收口到 `apps/api`
- `apps/web` 仅负责后台界面渲染、客户端访问控制与后端回源展示
- 订阅取消与恢复等用户动作优先直接调用 `apps/api`，不再依赖 `web` 侧 server action
- 管理页不再通过 `web` 侧 SSR 直接查询后台数据

## 5. 必须放在 `apps/api` 的能力

- Better Auth 与 OAuth 回调
- 数据库主读写能力
- 订阅、支付、积分、订单写操作
- 图片/视频去水印任务创建与状态更新
- SSE 用户事件流
- Webhook 回调
- R2 上传签名与服务端存储处理
- 后台管理数据接口（用户、订单、订阅、系统状态）

## 6. `packages/shared` 的职责

适合放入共享层的内容：

- TypeScript 类型
- API 响应结构
- i18n 字典与类型
- 常量与枚举
- 基础工具函数
- 被两端共用的服务封装

不建议过早放入共享层的内容：

- 尚未稳定的重业务模块
- 为单个产品特化的业务抽象

## 7. 新增功能时的判断顺序

新增需求时，建议按以下顺序判断：

1. 这是页面展示还是后端能力？
2. 是否涉及数据库写入、支付、上传、任务状态？
3. 是否属于多个位置都会复用的类型或工具？

落位规则：

- 页面 / UI / 路由 → `apps/web`
- 认证 / API / 存储 / 任务 / 支付 → `apps/api`
- 公共类型 / 常量 / 工具 → `packages/shared`

## 8. 当前关键路径

- Web 页面入口：`apps/web/src/app`
- API 路由入口：`apps/api/src/app/api`
- 共享库入口：`packages/shared/src/lib`
- 共享 i18n：`packages/shared/src/i18n`
- 数据库 schema：`packages/shared/src/lib/db/schema`

## 9. 代码评审自检清单

- 新页面是否把本应属于后端的逻辑写进了 `apps/web`？
- 新 API 是否应该放在 `apps/api/src/app/api`？
- 公共类型是否应该进入 `packages/shared`？
- 是否出现了前端和后端重复定义同一份 DTO？
- 是否误把平台密钥配置成了 `web` 必需环境变量？
